# 触发器与后端分层重构方案

## 1. 背景与目标

当前系统中，部分业务逻辑在**数据库触发器**与**后端服务层**中存在重复或职责交叉，例如：

- 帖子删除时的级联清理
- 帖子话题（Hashtag）提取与维护
- 用户更新时间维护
- 帖子情感分析初始化

这些重复会带来：

- 规则修改需要多处同步，容易漏改
- 行为难以通过单元测试和集成测试完全覆盖
- 数据问题排查困难（难以分辨是触发器还是后端导致）

本方案目标：

- 明确“哪些逻辑保留在触发器层，哪些逻辑下沉/上移到后端业务层”
- 给出每一项的**具体修改步骤**和**验证建议**
- 为后续重构提供一致的分层原则

---

## 2. 分层原则

统一采用以下分层策略：

1. **优先放在后端业务层的逻辑**
   - 与产品需求强相关、未来可能频繁变更的规则
   - 需要单元测试、性能测试、A/B 实验的逻辑
   - 依赖用户身份/角色/配置等业务上下文的判断
   - 与具体技术栈强相关（如 Java 正则解析、模型调用等）

2. **优先放在数据库触发器层的逻辑**
   - 安全/合规要求“一定不能被绕过”的规则（审计日志、敏感词预警）
   - 无论通过哪个入口（后端、脚本、手工 SQL）写数据，都必须统一执行的逻辑
   - 与业务解耦、变化频率较低的基础设施类规则

3. **应避免的模式**
   - 同一规则同时在：
     - 表定义（ON UPDATE/ON DELETE）
     - 触发器
     - 后端 SQL/Service
     三处（或两处）重复维护
   - 触发器中实现复杂的字符串解析、游标循环等业务逻辑，而后端已有可替代实现

## 3. 逐项调整方案

### 3.1 帖子情感分析初始化

**当前情况**

- 触发器：`tr_post_after_insert`  
  位置：`sql_scripts/04_create_triggers.sql:18-26`  
  功能：在 `posts` 插入后，如果 `post_sentiments` 没有对应记录，则插入一条：

  ```sql
  INSERT INTO post_sentiments (post_id, sentiment, confidence, analyzed_at, created_at)
  VALUES (NEW.post_id, 'UNANALYZED', NULL, NULL, NOW());
  ```

- 后端：
  - 原曾在 `PostService.createPost` 中插入 `UNANALYZED`，现已注释掉  
    位置：`backend/src/main/java/com/socialmedia/sentiment/service/PostService.java:73-76`
  - 现仅在异步情感分析后调用 `SentimentMapper.updateSentiment` 更新结果  
    位置：`backend/src/main/resources/mapper/SentimentMapper.xml:39-45`

**目标分层**

- 将“**每个帖子都必须有一条情感记录**”视为数据完整性约束，可保留在数据库层作为兜底。
- 后端仅负责触发异步分析与更新，不再承担初始化责任。

**实施措施**

1. **短期（推荐先采用）**
   - 保留触发器 `tr_post_after_insert`，不做修改。
   - 保持 `PostService.createPost` 中初始化情感记录的代码为注释状态或删除该段过期注释。

2. **如果未来希望完全迁移到后端**
   - 在 `PostService.createPost` 中恢复并改造初始化逻辑，使其具备幂等性，例如：
     - 使用 `INSERT INTO post_sentiments ... ON DUPLICATE KEY UPDATE ...`  
       或
     - 先通过 `SentimentMapper.findByPostId` 判断不存在再插入。
   - 在数据库中删除 `tr_post_after_insert` 触发器定义：
     - 从 `sql_scripts/04_create_triggers.sql` 中移除对应 `DROP TRIGGER IF EXISTS tr_post_after_insert;` 与 `CREATE TRIGGER tr_post_after_insert ...` 片段。
   - 执行变更后，针对帖子创建接口做回归测试，确认情感记录仍按期望生成。

### 3.2 用户更新时间维护（updated_at）

**当前情况**

- 表结构：`users.updated_at` 使用 `ON UPDATE CURRENT_TIMESTAMP` 自动更新时间  
  位置：`sql_scripts/01_create_tables.sql:18-19`
- 触发器：`tr_user_before_update` 再次手动设置 `updated_at = NOW()`  
  位置：`sql_scripts/04_create_triggers.sql:33-38`
- 后端：多处 SQL 更新中显式 `updated_at = NOW()`  
  位置示例：`backend/src/main/resources/mapper/UserMapper.xml:45-53,56-59`

**目标分层**

- 将 `updated_at` 视为技术性字段，由表定义自动维护即可。
- 删除触发器中的重复逻辑，并尽量减少 Mapper 内手动设置 `updated_at`。

**实施措施**

1. **删除触发器维护**
   - 在 `sql_scripts/04_create_triggers.sql` 中删除：
     - `DROP TRIGGER IF EXISTS tr_user_before_update;`
     - `CREATE TRIGGER tr_user_before_update ... END//` 整段。
   - 在数据库中执行对应的 `DROP TRIGGER`（如不通过脚本执行）。

2. **精简后端 Mapper**
   - 保留或简化 `UserMapper.update` 和 `UserMapper.updateStatus` 中的 SQL：
     - 可以去掉 `updated_at = NOW()`，依赖列定义自动更新。
     - 修改位置：`backend/src/main/resources/mapper/UserMapper.xml:45-53,56-59`

3. **验证**
   - 对用户信息更新、状态更新接口进行手工或自动化测试，确认 `updated_at` 仍能正确更新。

---

### 3.3 帖子删除链路（comments/post_hashtags/post_sentiments/alerts）

**当前情况**

- 表结构已定义外键级联：
  - `comments.post_id` → `posts.post_id` `ON DELETE CASCADE`  
    位置：`sql_scripts/01_create_tables.sql:50`
  - `post_hashtags.post_id` → `posts.post_id` `ON DELETE CASCADE`  
    位置：`sql_scripts/01_create_tables.sql:75`
  - `post_sentiments.post_id` → `posts.post_id` `ON DELETE CASCADE`  
    位置：`sql_scripts/01_create_tables.sql:90`

- 触发器：`tr_post_before_delete`  
  位置：`sql_scripts/04_create_triggers.sql:45-60`  
  行为：
  - 手动 `DELETE FROM comments/post_hashtags/post_sentiments`（与外键级联重复）
  - 删除 `alerts` 中 `content_type = 'POST' AND content_id = OLD.post_id` 的记录

- 后端：`PostService.deletePost`  
  位置：`backend/src/main/java/com/socialmedia/sentiment/service/PostService.java:127-144`  
  行为：
  - 校验权限后，依次调用：
    - `hashtagMapper.deletePostHashtagsByPostId(postId)`
    - `commentMapper.deleteByPostId(postId)`
    - `sentimentMapper.deleteByPostId(postId)`
    - `postMapper.deleteById(postId)`

**目标分层**

- 级联关系（评论、话题关联、情感记录）由**外键或后端中的一种负责即可**，不再由触发器重复实现。
- `alerts` 的清理逻辑应集中在后端业务层，方便扩展与测试。

**实施措施**

1. **后端承担业务级删除逻辑，触发器只负责数据级别最小职责（可选）**
   - 推荐完全移除 `tr_post_before_delete` 触发器：
     - 在 `sql_scripts/04_create_triggers.sql` 中删除 `tr_post_before_delete` 的触发器定义。
   - 在后端增加对 `alerts` 的删除逻辑：
     - 在 `PostService.deletePost` 中注入 `AlertService`（或相应 Mapper），增加：
       - 删除与该帖子相关的 `alerts` 记录（`content_type='POST', content_id=postId`）。
     - 修改位置：`backend/src/main/java/com/socialmedia/sentiment/service/PostService.java:127-144`
   - 后端可以选择继续显式删除 `comments/post_hashtags/post_sentiments`，也可以改为仅删除 `posts`，依赖外键级联：
     - 若选择依赖外键级联，可以删除：
       - `hashtagMapper.deletePostHashtagsByPostId(postId)`
       - `commentMapper.deleteByPostId(postId)`
       - `sentimentMapper.deleteByPostId(postId)`

2. **验证**
   - 针对帖子删除接口编写或扩展集成测试：
     - 确认帖子被删除后：
       - 评论、话题关联、情感记录均被删除（通过外键或后端逻辑）
       - `alerts` 中对应记录消失

### 3.4 评论删除与预警（COMMENT alerts）

**当前情况**

- 触发器：`tr_comment_before_delete`  
  位置：`sql_scripts/04_create_triggers.sql:67-73`  
  行为：
  - 在评论删除前，删除 `alerts` 中 `content_type='COMMENT' AND content_id=OLD.comment_id` 的记录。

- 后端：`CommentService.deleteComment`  
  位置：`backend/src/main/java/com/socialmedia/sentiment/service/CommentService.java:76-90`  
  行为：
  - 校验评论存在与权限后，仅调用 `commentMapper.deleteById(commentId)`。

**目标分层**

- 将“删评论时同时删对应预警”视为业务规则，由后端统一负责。
- 保证后续如增加更多类型预警时，逻辑集中在服务层。

**实施措施**

1. **后端接管预警删除**
   - 在 `CommentService` 中注入 `AlertService` 或对应 Mapper。
   - 在 `deleteComment` 中，在 `commentMapper.deleteById(commentId)` 之前或之后，增加：
     - 删除 `alerts` 中 `content_type='COMMENT' AND content_id=commentId` 的记录。
   - 修改位置：`backend/src/main/java/com/socialmedia/sentiment/service/CommentService.java:76-90`

2. **删除触发器**
   - 从 `sql_scripts/04_create_triggers.sql` 中移除 `tr_comment_before_delete` 的定义。
   - 在数据库执行 `DROP TRIGGER IF EXISTS tr_comment_before_delete;`。

3. **验证**
   - 对评论删除接口做回归测试：
     - 有命中敏感词的评论被删除时，预警一并被删除。

### 3.5 用户删除链路（User 级联）

**当前情况**

- 表结构：
  - `posts.user_id` → `users.user_id` `ON DELETE CASCADE`  
    位置：`sql_scripts/01_create_tables.sql:35`
  - `comments.user_id` → `users.user_id` `ON DELETE CASCADE`  
    位置：`sql_scripts/01_create_tables.sql:51`

- 触发器：`tr_user_before_delete`  
  位置：`sql_scripts/04_create_triggers.sql:80-104`  
  行为：
  - 删除该用户的所有评论
  - 使用游标逐条删除该用户的所有帖子（试图触发帖子的删除触发器）
  - 末尾有“删除用户的预警记录”注释但未实现具体 SQL

- 后端：`UserService.deleteUser`  
  位置：`backend/src/main/java/com/socialmedia/sentiment/service/UserService.java:97-101`  
  行为：
  - 校验用户存在后，仅调用 `userMapper.deleteById(userId)`。

**目标分层**

- 用户相关的级联删除主导权交给外键和业务层，不再使用游标驱动的触发器。
- 若需要删除与用户相关的 `alerts` 等业务数据，应在后端集中实现。

**实施措施**

1. **删除触发器**
   - 从 `sql_scripts/04_create_triggers.sql` 中移除 `tr_user_before_delete` 定义。
   - 在数据库执行 `DROP TRIGGER IF EXISTS tr_user_before_delete;`。

2. **可选：在后端补充用户级业务清理**
   - 根据业务需要，在 `UserService.deleteUser` 中注入 `AlertService` 等：
     - 删除该用户作为内容作者或评论者时产生的预警（如有需要）。
   - 位置：`backend/src/main/java/com/socialmedia/sentiment/service/UserService.java:97-101`

3. **验证**
   - 删除用户后检查：
     - 相关 `posts`、`comments` 是否按外键级联删除。
     - 若实现了预警清理，确认相关 `alerts` 被删除。

### 3.6 帖子话题提取（Hashtags）

**当前情况**

- 触发器：`tr_post_extract_hashtags`  
  位置：`sql_scripts/04_create_triggers.sql:112-164`  
  行为：
  - 使用游标与字符串函数从 `NEW.content` 中解析 `#话题#`，插入 `hashtags` 与 `post_hashtags`。

- 后端：
  - 工具类 `HashtagExtractor` 使用正则表达式解析话题  
    位置：`backend/src/main/java/com/socialmedia/sentiment/util/HashtagExtractor.java:17-33`
  - `PostService.createPost` 调用 `HashtagExtractor` 并维护 `hashtags/post_hashtags`  
    位置：`backend/src/main/java/com/socialmedia/sentiment/service/PostService.java:62-71`

**目标分层**

- 话题解析属于业务展示与统计相关逻辑，**应统一在后端实现**。
- 删除触发器中的重复实现，避免双重插入和大小写风格不一致。

**实施措施**

1. **保留后端逻辑不变**
   - `HashtagExtractor` 和 `PostService.createPost` 当前实现已经满足需求，无需变更。

2. **删除触发器实现**
   - 从 `sql_scripts/04_create_triggers.sql` 中移除 `tr_post_extract_hashtags` 触发器定义。
   - 在数据库执行 `DROP TRIGGER IF EXISTS tr_post_extract_hashtags;`。

3. **验证**
   - 发布包含多个 `#话题#` 的帖子：
     - 确认 `hashtags` 与 `post_hashtags` 正常插入。
     - 验证前端话题列表、热门话题统计接口是否正常工作。

### 3.7 关键词审计日志（audit_logs）

**当前情况**

- 触发器：
  - `tr_keyword_audit_update`：更新时写入 `old_values/new_values`  
    位置：`sql_scripts/04_create_triggers.sql:171-185`
  - `tr_keyword_audit_insert`：插入时写入 `new_values`  
    位置：`sql_scripts/04_create_triggers.sql:192-205`
  - `tr_keyword_audit_delete`：删除时写 `old_values`  
    位置：`sql_scripts/04_create_triggers.sql:212-225`
- 后端：
  - `KeywordService` 只做关键词 CRUD 与去重校验  
    位置：`backend/src/main/java/com/socialmedia/sentiment/service/KeywordService.java`
  - 未实现审计日志逻辑。

**目标分层**

- 审计日志属于安全与可追溯性需求，保留在数据库触发器层。
- 后端不需要重复实现审计逻辑。

**实施措施**

1. **保持现有触发器实现，不做迁移**
   - 不在后端增加类似逻辑，避免重复。

2. **文档化约束**
   - 在开发规范中说明：直接对 `keywords` 表执行 SQL 操作仍会生成审计记录，保持与服务层行为一致。

3. **验证**
   - 针对关键词增删改，通过接口与直接 SQL 各执行一次，确认 `audit_logs` 记录完整且字段符合预期。

### 3.8 敏感词预警（alerts 生成）

**当前情况**

- 触发器：
  - `tr_post_keyword_check`：帖子插入后检测敏感词并插入 `alerts`  
    位置：`sql_scripts/04_create_triggers.sql:232-271`
  - `tr_comment_keyword_check`：评论插入后检测敏感词并插入 `alerts`  
    位置：`sql_scripts/04_create_triggers.sql:278-321`

- 后端：
  - `AlertService` 与 `AdminController` 负责 `alerts` 的查询、标记已处理、删除  
    位置：`backend/src/main/java/com/socialmedia/sentiment/service/AlertService.java`  
          `backend/src/main/java/com/socialmedia/sentiment/controller/AdminController.java:179-227`
  - 未在服务层实现敏感词扫描与预警生成逻辑。

**目标分层**

- 保持敏感词预警逻辑在数据库层，保证无论通过何种入口写入帖子/评论都能触发预警。
- 后端只负责预警的查看与处置（标记已处理、删除）。

**实施措施**

1. **触发器保持现状**
   - 不将预警生成迁移到后端，避免在两个层面重复扫描内容。

2. **后端增强（可选）**
   - 未来若需要引入更复杂的预警规则（如模型评分），可以在触发器逻辑基础上，在后端叠加一层额外预警，而不是替代现有触发器。

3. **验证**
   - 创建包含敏感关键词的帖子/评论：
     - 确认 `alerts` 表中生成对应记录。
     - 通过管理端接口能正确查询到预警并进行处理。

## 4. 推荐实施顺序

建议按以下顺序逐步实施，以降低风险：

1. **先移除纯技术性重复逻辑**
   - 删除 `tr_user_before_update`（3.2）
   - 验证 `updated_at` 行为正确

2. **重构话题提取逻辑**
   - 删除 `tr_post_extract_hashtags`（3.6）
   - 保留后端 `HashtagExtractor` 与 `PostService.createPost`
   - 验证话题展示与统计

3. **重构帖子/评论删除链路**
   - 修改 `PostService.deletePost` 和 `CommentService.deleteComment`，将 `alerts` 清理迁移至后端（3.3、3.4）
   - 删除 `tr_post_before_delete` 与 `tr_comment_before_delete`
   - 验证删除接口行为

4. **重构用户删除链路**
   - 删除 `tr_user_before_delete`，如有需要在 `UserService.deleteUser` 中添加业务清理（3.5）
   - 验证用户删除及级联效果

5. **保留并验证审计与预警逻辑**
   - 保留关键词审计触发器与敏感词预警触发器（3.7、3.8）
   - 通过接口和直接 SQL 进行端到端验证

---

## 5. 验证与回归测试建议

为保证重构安全，建议在每一步后至少完成以下验证：

1. **接口级集成测试**
   - 用户注册/状态更新/删除
   - 发帖/删帖
   - 评论/删评论
   - 关键词管理（增删改）
   - 预警查询与处理

2. **数据一致性检查**
   - 随机抽取若干用户，检查其相关帖子、评论、话题、情感记录、预警是否一致。
   - 对比触发器重构前后的统计接口结果（如情感分布、热门话题）。

3. **回滚策略**
   - 在每次删除触发器之前保留对应 SQL 片段备份。
   - 如出现异常，可通过重新执行 `CREATE TRIGGER` 语句快速恢复。

---

## 6. 总结

通过本次分层重构：

- **业务逻辑**（话题解析、删除规则等）将集中在后端服务层，更易于测试与演进。
- **安全与审计类逻辑**（关键词审计日志、敏感词预警）保留在触发器层，确保任何入口写入都受控。
- 冗余的触发器逻辑被移除，减少“同一规则多处实现”的维护成本。

后续如新增业务需求，可优先在服务层实现，在确有必要时再考虑下沉到数据库层，遵循本方案的分层原则。
